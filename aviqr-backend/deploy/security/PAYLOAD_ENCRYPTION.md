# Sensitive API data and payload encryption

The web and Expo clients encrypt JSON request bodies as compact JWE using RSA-OAEP-256 and AES-256-GCM. Each request has a fresh AES key, nonce, and request ID. Only the gateway private key decrypts the body. Login, registration, OTP, password changes/resets, refresh, account changes, tenant settings, PMS, payments, and AI JSON calls use this mechanism through shared clients. Browser DevTools shows `{ "jwe": "..." }` on the wire. The original form values still exist in client memory; application encryption cannot protect a compromised client or hide values from its owner.

The gateway decrypts before authentication/routing and forwards the original JSON to services. Encrypted plaintext contains the method, exact path and query, issue time, request ID, and original body. Requests expire after 120 seconds with 30 seconds of future clock tolerance. Redis reserves IDs for 180 seconds across gateway instances; duplicates are rejected, and Redis failure returns 503. Authentication challenge retries encrypt the original body again with a fresh ID. JSON envelopes are limited to 1 MiB. JSON service responses, URLs, authorization headers, multipart uploads, and externally signed provider webhooks use HTTPS without this envelope. Keep secrets out of URLs.

Production and staging reject plaintext JSON by default and require a provisioned key. Development creates an ephemeral RSA key and allows old plaintext clients for local compatibility, while the updated clients still encrypt JSON. Payment, aggregator and channel-manager provider webhooks preserve their original formats and existing signature/shared-secret validation. TLS remains mandatory for all API transport; the extra envelope does not replace TLS (see [OWASP TLS guidance](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)).

## Deployment

1. Run `bash deploy/security/generate-payload-key.sh /secure/new-payload-key-directory` on a trusted host. It writes a 3072-bit RSA key and a private `payload.env` containing base64 PKCS8 `PAYLOAD_ENCRYPTION_PRIVATE_KEY`. Keep the output outside the repository and install the same environment value on every blue/green gateway. Gateway startup fails if production/staging lacks the key. Do not expose it through Vite or Expo environment variables.
2. For a coordinated rollout with existing mobile builds, initially set gateway `PAYLOAD_ENCRYPTION_REQUIRED=false`. This permits old JSON clients while HTTPS remains mandatory and the stable key remains required. Deploy the gateway first, then web/mobile clients; enforce the default `true` after old mobile builds have been upgraded or retired. Deploying strict enforcement immediately rejects old clients.
3. Configure `EXPO_PUBLIC_STAGING_API_URL` in the EAS `preview` environment with the real staging HTTPS endpoint. The EAS staging build profile sets `EXPO_PUBLIC_APP_ENV=staging`; local `android:staging` and `ios:staging` scripts validate that the URL is present and HTTPS. The previous public HTTP staging address is removed. Production mobile uses `https://api.aviqr.com`, and production web defaults to the same endpoint. Development retains local HTTP.
4. Apply the reviewed Nginx changes from `deploy/nginx/aviqr.conf` (and its reference copy), validate with `nginx -t`, and reload. They add HSTS and reject HTTP API requests with 426. These files are not automatically deployed. Gateway HTTPS enforcement trusts `X-Forwarded-Proto` only from configured `app.trusted-proxy-ips`; restrict public gateway/service ports and have Nginx overwrite the protocol header.
5. Apply the shop-service Liquibase migration, which expands encrypted credential columns to TEXT. Provision the existing `INTERNAL_SYNC_SECRET` encryption key before saving tenant credentials. SMTP password, Twilio token, WhatsApp API key, FCM key, and Razorpay secrets encrypt on write and are omitted from ordinary settings JSON responses. Run one shop-service instance with `CREDENTIAL_ENCRYPTION_BACKFILL=true` to encrypt existing plaintext values in locked batches of 100, then disable it. This migration has not been run against a live database. Legacy plaintext remains readable until migrated; protect backups containing the old values.
6. Check an encrypted login and refresh from each client; verify DevTools has a JWE body, requests reach normal DTO validation, and replaying the identical ciphertext is rejected. Check key lookup from the actual web origin, upload flows, AI streaming, and provider webhooks. Service-to-service transport remains private HTTP in the current configuration; use TLS/mTLS if services run across an untrusted network.

All gateway instances must share the key, trusted proxy configuration, and Redis. Changing the RSA key invalidates requests encrypted with the old public key; clients cache it for 60 seconds. This implementation has one active key, so rotate during a coordinated restart/retry window rather than changing one gateway in a rolling deployment. Tenant credential encryption currently derives its AES key from `INTERNAL_SYNC_SECRET`; preserve it until a separate decrypt/re-encrypt key migration is implemented.

## Review findings and validation limits

Passwords already use BCrypt (cost 12); refresh tokens and OTPs are hashed. Native session credentials use Expo SecureStore, and web session credentials use memory/HttpOnly cookies. OTP and password-reset application log messages no longer include email addresses. API responses now carry `Cache-Control: no-store`.

PMS channel access keys and webhook secrets are still plaintext database fields, and authorized channel-management responses intentionally return them for configuring integrations. They travel in encrypted JSON requests and HTTPS responses. Encrypting those database fields needs a separate compatible migration because inbound booking authentication currently queries by access key. Customer/guest PII, database volumes/backups, provider logs, and arbitrary business audit messages are not certified as encrypted or redacted by this source review.

The web client uses built-in Web Crypto. Native Expo uses Forge for RSA-OAEP/AES-GCM with entropy supplied by Expo Crypto, including an explicit OAEP seed. Forge 1.4.0 has an unpatched [PKCS#1 v1.5 signature-verification advisory](https://github.com/advisories/GHSA-86w9-cpqp-85rv). This implementation never performs that signature-verification operation; the dependency advisory remains relevant for dependency auditing and future library use. Existing dependency audit issues remain in the projects.

Focused gateway, web, and mobile logic tests cover encryption interoperability, Unicode bodies, randomized ciphertext, retries, tampering, expiry, request binding, replay rejection, Redis failure, CORS, transport protection, credential serialization, and secure session storage. The web production build and Expo Android, iOS, and web exports pass. Metro requires image-size 1.x for its asset pipeline; do not override it to 2.x. No production deployment, live login using the supplied credentials, key provisioning, or database backfill has been performed.
